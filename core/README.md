# Ядро Bootloader-а

Здесь содержится platform- и board-независимый код Bootloader-а. Ядро общается с внешним миром через реализации API-функций, объявленных в файле ```bootloader_port.h```.

## Тайм-аут ожидания активации

Если в `bootloader_project_config.h` определён `BOOTLOADER_TIMEOUT_MS`,
его значение задаёт тайм-аут по умолчанию в миллисекундах. Проект может
переопределить его перед `InitBootloader()`:

```c
#include "bootloader.h"

/* В коде запуска, перед InitBootloader(): */
BootloaderSetActivationTimeout(30000);
InitBootloader();
```

Последний вызов задаёт значение. `InitBootloader()` не сбрасывает его,
а фиксирует начало отсчёта после проверки приложения. Без вызова API
сохраняется значение из конфигурации. Значение `0` разрешает запуск
исправного приложения без дополнительного ожидания при обработке автомата.
После активации загрузчика тайм-аут не вызывает запуск приложения;
при повреждённом приложении загрузчик продолжает работу.

Без `BOOTLOADER_TIMEOUT_MS` функция переопределения недоступна,
сохраняется режим активации через `port_boot_jumper_is_active()`.

## Настройка команды запуска приложения

Настройки ядра задаются в `bootloader_project_config.h` конкретного проекта.
Чтобы игнорировать команду запуска приложения, определить:

```c
#define BOOTLOADER_DISABLE_APP_RUN_CMD
```

После активации загрузчика команда `CMD_APP_RUN` (`0x76`) возвращает ОК,
но загрузчик продолжает принимать команды. Проверки завершения записи и
целостности образа для этой команды не выполняются; периферия не
деинициализируется и управление приложению не передаётся.

Опция действует только на команду запуска. Автоматический запуск исправного
приложения без активации загрузчика, в том числе по `BOOTLOADER_TIMEOUT_MS`,
сохраняется. Если define отсутствует, команда работает в обычном режиме.

## Команды протокола V2

Команды доступны после ACTIVATE либо активации через существующий
`port_boot_jumper_is_active()`. Запрос каждой команды состоит ровно из
одного байта. До активации и при неверной длине запрос игнорируется,
как и другие некорректные запросы ядра. Настройки активации не меняются.

### GET_FIRMWARE_HASH — 0x79

Перед каждым ответом ядро рассчитывает Poly1305 MAC всей области приложения
без последних 16 байт и сравнивает его с MAC в конце области. Проверка
выполняется и при `BOOTLOADER_DBG_MODE`.

При несовпадении возвращается `79 01`. При совпадении ответ содержит
18 байт: `79 00 [HASH:16]`. Хэш передаётся как исходные 16 байт без
преобразования порядка байтов или представления в строку.
Результат проверки также обновляет внутренний флаг целостности прошивки.

Раскладка области приложения:

```text
[Бинарник][Заполнитель FF][Хэш исходного бинарника:16][MAC:16]
```

Полный хвост занимает 32 байта и входит в `BOOTLOADER_APP_LENGTH`.
Начало хэша: `BOOTLOADER_APP_BEGIN + BOOTLOADER_APP_LENGTH - 32`.
Начало MAC: `BOOTLOADER_APP_BEGIN + BOOTLOADER_APP_LENGTH - 16`.
Генератор записывает хэш до расчёта MAC; хэш входит в защищённую область.
Linker-файл приложения исключает последние 32 байта из размещения кода.
Ядро не рассчитывает хэш исходного bin и не определяет его алгоритм:
оно проверяет MAC и возвращает сохранённые байты хэша.

Версия приложения в хвосте больше не хранится. Старые образы с версией
перед MAC нужно пересоздать новым генератором: правильный MAC сам по себе
не позволяет ядру отличить прежнюю раскладку хвоста от новой.

Расчёт MAC синхронный: при запросе хэша обработка команд приостанавливается
на время чтения всей области приложения. Это нужно учитывать в таймауте ПК.

### GET_DEVICE_ID — 0x7A

Ответ содержит 34 байта: `7A 00` и 32 байта идентификатора устройства.
Используется `BOOTLOADER_DEVICE_ID_STRING`, тот же идентификатор, который
проверяется в идентификационном блоке команды BEGIN. Свободные байты
заполнены нулями. Строка должна быть ASCII и занимать не более 32 байт
без завершающего нуля; превышение длины вызывает ошибку сборки.
При длине ровно 32 байта завершающий ноль в ответ не входит.

Команда не требует наличия прошивки и не выполняет проверку MAC.

## Несколько экземпляров Binex

Каждый канал использует свой статический `Binex_t`, собственный буфер приёма
и функцию вывода символа. Все состояния приёмника и передатчика, включая
счётчики, экранирование и CRC передачи, находятся внутри экземпляра.
Динамическая память не используется; буферы в структуру не встроены.

Перед обменом один раз вызывается `Crc16Init()`, затем для каждого канала:

```c
binex_init(&channel, channel_putc);
binex_receiver_begin(&channel, rx_buffer, sizeof(rx_buffer));
```

`channel_putc(uint8_t)` возвращает 1 при успешной передаче символа в поток
или 0, если поток заполнен. Все функции Binex принимают указатель на экземпляр
первым аргументом. Глобальной функции `binex_tx_callback()` больше нет.

Приём: `binex_receiver(&channel, c)`, длина готового пакета:
`binex_get_rxpack_len(&channel)`. Передача начинается вызовом
`binex_transmitter_init(&channel, tx_buffer, length)` и продолжается
`binex_transmit(&channel)` до `BINEX_PACK_TX`.

Один экземпляр нельзя одновременно обслуживать из прерывания и основного
цикла. Разные экземпляры не разделяют состояние обмена. Таблица CRC общая
и после `Crc16Init()` используется только для чтения.

Ядро загрузчика использует один собственный экземпляр. Формат пакетов,
проверка CRC, экранирование и поведение при заполнении UART не изменены.

## Опциональный прокси

`BOOTLOADER_USE_PROXY` включает команды A0–A4 для составного устройства.
Архитектура, API порта и требования к буферизации описаны в [PROXY.md](PROXY.md).
