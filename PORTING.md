# Портирование PolyBoot на другой микроконтроллер

Это инструкция для ИИ-агента и разработчика. Выполняй этапы по порядку:
параметры платы и памяти → порт → базовое демо → аппаратная проверка →
особенности платы и прокси. Источник контрактов — заголовки и код текущей
ревизии PolyBoot.

## 1. Правила работы для ИИ-агента

- Прочитай инструкции репозитория и существующие порты. Меняй только код,
  относящийся к переносу; не рефактори ядро и соседние проекты заодно.
- Не придумывай пины, частоту кварца, уровни активации, подтяжки, размеры
  памяти и полярность RESET/CS/DE. Неизвестные параметры уточни у заказчика.
- Используй библиотеки из указанного SDK или проверенного проекта.
  Сохрани лицензии и аппаратные обходные последовательности.
- Используй статические буферы. Не добавляй malloc, VLA, рекурсию,
  диспетчеры событий и универсальные драйверы без необходимости.
- Не добавляй блокирующее ожидание в основном цикле или ISR. Штатные операции
  Flash и однократная инициализация могут быть синхронными; их время учитывай
  при расчёте обмена. Не вводи произвольные таймауты аппаратуры.
- Если контракт ядра не реализуется на новом МК, останови зависимую часть
  работы и опиши ограничение. Не выдавай частичную реализацию за рабочий порт.
- Проверки прошивки выполняй на плате. Сборка и map проверяют компоновку,
  но не заменяют испытания. Не создавай симуляторы, моки и имитацию
  Flash/UART для объявления порта проверенным.
- В отчёте укажи файлы, настройки памяти, результаты сборки, расход ресурсов
  и аппаратные проверки. Непроверенное на плате обозначь явно.

## 2. Собери исходные данные

До написания аппаратного кода заполни таблицу.

| Что выяснить | Что зафиксировать |
| --- | --- |
| МК и инструмент | Полная маркировка, CPU, компилятор/версия, отладчик |
| Flash | База, объём, банки, границы и размер стирания области приложения |
| Запись Flash | Минимальная единица, выравнивание, ограничения повторной записи, ECC/cache |
| RAM | Доступные диапазоны, место стека, ограничения доступа CPU/DMA |
| Образы | Размер загрузчика, начало/длина приложения, исключённые настройки |
| Тактирование | Кварц/генератор, реальная частота, частоты CPU и шин |
| Связь с ПК | UART/другой поток, пины/MUX, скорость, формат, SWAP, DE/RE |
| Активация | Таймаут или внешнее условие, уровни, подтяжки, ранняя проверка GPIO |
| Остальная аппаратура | Watchdog после сброса, общие GPIO, условия запуска приложения |
| Для прокси | Число/ID слейвов, шины, RESET/CS, паузы выбора, расчёт буферов |

У текущего ядра есть предпосылки:

- Приложение читается как память по абсолютному адресу: так проверяется MAC
  и сравниваются записываемые данные.
- Стертая Flash содержит FF.
- Область приложения обходится с постоянным шагом
  `BOOTLOADER_FLASH_SECTOR_SIZE`.
- Примеры рассчитаны на little-endian Cortex-M. В Binex CRC поля длины
  вычисляется по представлению uint16_t в памяти. Для другого endian
  нужен отдельный разбор совместимости, не только новый UART-драйвер.
- Компилятор поддерживает `stdint.h`, `_Static_assert` и `#pragma pack`.
  Ассемблер перехода и startup соответствуют выбранному компилятору.

Не выбирай средний или минимальный сектор для неоднородной Flash.
Нужна область приложения с подходящей постоянной геометрией либо отдельно
согласованная адаптация. Внешняя Flash без отображения в память не
подключается одной заменой функции записи.

Имена `hw_*`, `SerialPort*` и `RingFIFO` — соглашения примеров, не API ядра.
Обязательные имена интеграции объявлены в `bootloader_port.h`.
Если HAL МК уже существует, используй его и добавь проект платы.
Не создавай копию HAL ради другого UART или кварца. Поддержку всего семейства
объявляй после проверки геометрии Flash, RAM, startup и различий устройств.

Если PolyBoot подключается к отдельному продукту субмодулем, допустима
структура продукта `external/PolyBoot/` и `source/`. Общий HAL и ядро
остаются в субмодуле, конфигурация и исходники платы — в source.
Переноси туда проектные файлы демо с пересчётом относительных include/source
путей. Не создавай вторую копию core или vendor-библиотеки ради интеграции.

| HAL микроконтроллера | Конкретный проект |
| --- | --- |
| Vendor CMSIS/SPL и лицензии | Кварц, PLL, скорость и пины интерфейса |
| Геометрия Flash, стирание и запись | Разбиение Flash, Device ID, ключи |
| Переход для CPU/компилятора | UART FIFO, ISR, GPIO входа, DE, CS, RESET |
| Исходная полная карта памяти | Рабочие linker-файлы и настройки сборки |
| Код, не зависящий от платы | Инициализация платы, активация и прокси-порт |

Не зашивай кварц платы в общий vendor-файл HAL. Проверь, как SDK получает
его частоту: через проектный conf или define для всех единиц трансляции.
В AT32 она задаётся в конфигурации проекта. В GD32 часть системных файлов
лежит в проекте из-за особенностей конфигурирования SDK.

Образцы структуры и API: [HAL AT32F435](hal/at32f435vgt7/README.md) и
[обычное демо F435](project/at32f435vgt7-uart-bootloader/README.md).
Регистры и аппаратные константы другого МК переносить механически нельзя.

## 4. Рассчитай память и настрой конфигурацию

```text
APP_BEGIN = BOOTLOADER_APP_BEGIN
APP_LENGTH = BOOTLOADER_APP_LENGTH
APP_END = APP_BEGIN + APP_LENGTH       # адрес сразу после области
HASH_BEGIN = APP_END - 32
MAC_BEGIN = APP_END - 16

[Исходный bin][Заполнитель FF][Хэш bin:16][MAC:16]
```

Хэш занимает `[APP_END - 32, APP_END - 16)`, MAC — `[APP_END - 16, APP_END)`.
MAC считается по `[APP_BEGIN, APP_END - 16)`, включая хэш. APP_LENGTH
больше 32 и включает заполнитель, хэш и MAC. Версии в хвосте больше нет.

Согласуй конфигурацию загрузчика, linker загрузчика, linker приложения
и генератор. При изменении размера загрузчика недостаточно исправить
только BOOTLOADER_APP_BEGIN.

- Все readonly-секции загрузчика помещаются до APP_BEGIN.
- APP_BEGIN и APP_LENGTH соответствуют границам стирания.
- Настройки и иные сохраняемые области не входят в APP_LENGTH.
- Последний адрес ROM приложения в linker-файле — `APP_END - 33` включительно.
- Векторы приложения находятся в APP_BEGIN и имеют требуемое CPU выравнивание.
  Первые два слова — начальный MSP и Reset_Handler.
- RAM, стек и heap задаются по новому МК, не копируются вслепую.
- Учитывается шаг аппаратной защиты загрузчика. Настройку option bytes
  выполняй только в согласованном объёме работ.

Пример AT32F435VGT7, не универсальные значения для нового МК:

| Область | Адреса |
| --- | --- |
| Загрузчик, 16 Кбайт | `0x08000000–0x08003FFF` |
| Приложение, 1006 Кбайт | `0x08004000–0x080FF7FF` |
| Хэш | `0x080FF7E0–0x080FF7EF` |
| MAC | `0x080FF7F0–0x080FF7FF` |
| Настройки, 2 Кбайт | `0x080FF800–0x080FFFFF` |

### Конфигурационные файлы

`hal/<mcu>/port/inc/bootloader_hal_config.h` задаёт
`BOOTLOADER_FLASH_SECTOR_SIZE` в байтах для порта.

`project/.../config/bootloader_project_config.h` задаёт:

| Определение | Смысл |
| --- | --- |
| `BOOTLOADER_APP_BEGIN` | Абсолютный адрес векторов приложения |
| `BOOTLOADER_APP_LENGTH` | Вся обновляемая область, включая хвост 32 байта |
| `BOOTLOADER_DEVICE_ID_STRING` | ASCII ID типа устройства, до 32 байт без терминатора |
| `BOOTLOADER_RESPONSE_DELAY_MS` | Задержка обычных ответов в миллисекундах |
| `BOOTLOADER_TIMEOUT_MS` | Наличие включает командную активацию и автозапуск по таймауту |
| `BOOTLOADER_DISABLE_APP_RUN_CMD` | Команда 76 отвечает OK, но не запускает приложение |
| `BOOTLOADER_USE_PROXY` | Включает A0–A4 и API порта прокси |
| `BOOTLOADER_DBG_MODE` | Пропускает только стартовую проверку MAC; для приёмки не включать |
| `BOOTLOADER_USE_USER_DATA` | Дополнительное стирание пользовательской области; см. ограничение ниже |

`BOOTLOADER_UART_BAUD` используется драйверами примеров; ядро не настраивает
UART и не требует конкретной скорости.

При ID ровно 32 байта терминатор в GET_DEVICE_ID не передаётся, при меньшей
длине ответ дополнен нулями. Длина проверяется `_Static_assert`.
Идентификационный блок BEGIN остаётся 128-байтным.

`config/private_keys.inc` содержит массивы `EncryptionKey` и `IntegrityKey`
по 32 байта. Они совпадают с ключами соответствующей секции генератора.
Демо-ключи публичны; рабочие ключи получает заказчик. Не генерируй и не
заменяй ключи без задания, не выводи их значения в отчёт.

**Ограничение USER_DATA.** Текущий код использует имена `USER_DATA_BEGIN`,
`USER_DATA_LENGHT` (именно такое написание) и `FLASH_SECTOR_SIZE`.
AT32-порты при этом ограничивают стирание областью приложения.
Недостаточно включить define для отдельной области настроек: надо отдельно
согласовать её доступность для Flash API и геометрию. В новом базовом
порте этот режим по умолчанию не включать.

## 5. Реализуй обязательный API

Прототипы: [core/inc/bootloader_port.h](core/inc/bootloader_port.h).
Каждый символ реализуется ровно один раз: Flash и переход обычно в HAL,
связь с платой и deinit — в проекте.

### Flash

```c
uint8_t port_sector_isclear(uint32_t sector);
uint8_t port_sector_erase(uint32_t address);
uint8_t port_write_chunk(uint8_t *chunk, uint32_t address, uint16_t len);
```

| Функция | Контракт |
| --- | --- |
| `port_sector_isclear` | sector — абсолютное начало сектора. Проверить весь сектор, не только первое слово. Возврат **1**, только если все байты FF; иначе **0**. Память не менять. |
| `port_sector_erase` | address — абсолютное начало сектора, не номер и не смещение от APP_BEGIN. Стереть один целый сектор. Возврат **0** при успехе, ненулевое значение при ошибке. |
| `port_write_chunk` | Записать ровно len байт по абсолютному address, проверить чтением. Возврат **0** при успехе, ненулевое значение при ошибке. Не стирать Flash внутри записи. |

При BEGIN ядро проходит всю область приложения: пустые сектора пропускает,
непустые стирает и снова проверяет через port_sector_isclear.
**Результат port_sector_erase сейчас не используется ядром**: успешность
определяется фактическим FF. Одного кода возврата SDK недостаточно.

Перед записью ядро сравнивает Flash и блок; совпадающий блок не пишет.
Обычно блок содержит до 128 байт, но len может быть меньше, адрес и исходный
указатель не обязаны быть выровнены. Протокол не требует последовательных
адресов или передачи всех блоков. Пустые FF-блоки могут отсутствовать
в файле, поскольку BEGIN уже подготовил всю область.

В реализации порта:

1. Ограничь всю операцию разрешённой областью. Сектор целиком внутри неё
   и выровнен; запись не пересекает APP_END. Проверки не должны обходиться
   переполнением сложения address + len.
2. Не затрагивай загрузчик, соседние байты и настройки. Хэш и MAC находятся
   ВНУТРИ приложения и должны записываться.
3. Выбирай банк и его флаги по адресу текущей операции. Блок может пересечь
   границу банков; одного выбора банка на весь блок может быть недостаточно.
4. Соблюдай ограничения записи МК. Не читай невыровненный исходный буфер
   приведением uint8_t* к uint32_t*.
5. Сохрани PRIMASK перед запретом IRQ, восстанови его после операции,
   включая ошибку. Безусловный __enable_irq меняет состояние вызывающего
   кода. Контроллер Flash после операции снова блокируется.
6. Учти ECC/cache: проверка должна видеть реальные новые данные. Если SDK
   требует выполнение из RAM, перенеси нужные функции/константы средствами
   линкера и проверь map.

Если МК допускает только крупную единицу записи, которую нельзя безопасно
дописывать, не имитируй произвольную байтовую запись стиранием сектора.
Согласуй ограничение или способ адаптации: это влияет на сохранность данных.

### Поток связи с ПК

```c
int16_t port_serial_putc(uint8_t c);
int16_t port_serial_getc(void);
int port_serial_transfer_completed(void);
```

| Функция | Контракт |
| --- | --- |
| `port_serial_putc(c)` | c, если байт принят в TX FIFO/передатчик; **-1**, если места нет. Байт 00 возвращается как 0 и является успехом. Не ждать свободного места. |
| `port_serial_getc()` | 0..255 — следующий байт; **-1** — данных нет. Не ждать прихода байта. |
| `port_serial_transfer_completed()` | **1**, если очередь пуста И последний байт физически передан; иначе **0**. Проверять TC/TDC, не только FIFO или TDBE. |

Не возвращай из putc логические 0/1 вместо c/-1. У callback Binex другой
контракт: `return port_serial_putc(c) == c;`. Иначе ломается, например, байт 00.

ISR обслуживает периферию и FIFO, TX IRQ и аппаратные ошибки.
ProcessBootloader работает в main. Из ISR не запускай ядро или Flash API.
Короткие критические секции FIFO также восстанавливают исходный PRIMASK.

Для RS485 проверь DE/RE и окончание последнего стоп-бита. Для USB/другого
транспорта реализуй те же семантики потока; ядро не должно узнавать
конкретную периферию. Переполнение и аппаратная потеря байтов учитываются
проектом, а не выдаются за успешный обмен.

### Активация, освобождение аппаратуры и переход

```c
int port_boot_jumper_is_active(void);
void port_deinit_all(void);
void port_application_run(void);
```

`port_boot_jumper_is_active()` возвращает **1** для активного условия входа
и **0** для неактивного. Название историческое: это GPIO, состояние линий
или уже принятое в main решение. Сам интерфейс функция не инициализирует
и ответов ПК не отправляет.

`port_deinit_all()` освобождает всё, настроенное загрузчиком на плате.
Он не выполняет переход. Правила очистки — в разделе 7.

`port_application_run()` читает начальный MSP и Reset_Handler из векторов
приложения, передаёт управление без возврата. Аппаратный deinit уже выполнен
вызывающим кодом; функция перехода остаётся низкоуровневой.

## 6. Обеспечь миллисекундный счётчик и запуск

Ядро включает проектный `systick.h` и использует `SYSTICK_GET_VALUE()`.
Это беззнаковый 32-битный счётчик миллисекунд. Он работает до вызова
InitBootloader и всё время обслуживания ядра; разности считаются
с учётом обычного переполнения uint32_t. Допустим другой аппаратный таймер,
но единица измерения остаётся 1 мс.

IRQ-счётчик объяви volatile. В примерах SysTick_Handler только увеличивает
его. LOAD рассчитывается по реальному источнику SysTick: AHB и AHB/8
дают разные значения. Константа 24999 из демо не универсальна.

Типовая последовательность AT32-проекта:

```c
void main(void)
{
  hw_system_clock_config();
  SerialPortInit();           /* FIFO готовы до разрешения IRQ UART. */
  hw_config();               /* GPIO, UART, NVIC и SysTick. */
  InitBootloader();

  for (;;)
    ProcessBootloader();
}
```

InitBootloader вызывается один раз при входе в загрузчик. В нём
инициализируются CRC/Binex и флаги, проверяется MAC приложения.
Не вызывай его заново при выборе слейва или включении UART: это сбрасывает
состояние незавершённого обновления.

Аппаратные функции примера проектные. Не дублируй инициализацию SysTick/UART,
если её уже делает hw_config. Имена IRQ должны точно совпадать со startup.

### Выбери режим активации

| Настройка | Поведение текущего ядра |
| --- | --- |
| BOOTLOADER_TIMEOUT_MS определён | Init проверяет MAC и запускает таймер. Без ACTIVATE исправное приложение запускается после таймаута. Внешняя перемычка не опрашивается. |
| Define таймаута отсутствует, jumper = 1 | Ядро сразу активировано; команда ACTIVATE не нужна. Автозапуск подавлен. |
| Define таймаута отсутствует, jumper = 0 | Исправное приложение запускается при обслуживании ядра; повреждённое оставляет загрузчик ждать ACTIVATE. |

Таймаут 0 не отключает его ветвь: для внешнего режима нужно убрать define.
Наличие `BOOTLOADER_DISABLE_APP_RUN_CMD=0` также включает опцию;
выключение — удалить define.

Таймер автозапуска начинается ПОСЛЕ стартового расчёта MAC. После активации
таймаут больше не запускает приложение. BOOTLOADER_DISABLE_APP_RUN_CMD
запрещает только переход по команде 76, а не автоматический переход
неактивированного загрузчика.

Ранняя проверка GPIO до тактирования и прямой переход из main — отдельная
политика платы. Такой переход обходит проверку MAC ядром. Не добавляй его
автоматически в базовое демо; согласуй условие и состояние аппаратуры.

## 7. Реализуй deinit и передачу управления

Составь пары init/deinit по каждому изменённому ресурсу:

| Настроено | Что освободить перед приложением |
| --- | --- |
| SysTick/таймер | Остановить, отключить его IRQ, очистить pending и используемый счётчик |
| UART/DMA | Отключить запросы/IRQ, остановить DMA, сбросить периферию и FIFO |
| NVIC | Отключить задействованные IRQ, очистить pending, восстановить изменённые приоритеты/группировку |
| GPIO/MUX | Вернуть изменённые пины, снять DE/CS и управляющие сигналы |
| Тактирование | Безопасно перейти на согласованный исходный источник, затем отключить PLL/источники и clocks периферии |
| Flash/PWC/cache | Вернуть изменённые настройки в безопасном порядке для текущей частоты |

Используй штатный сброс периферийного блока, если он очищает именно ресурс,
которым владел загрузчик. Не сбрасывай целый GPIO-порт при закрытии прокси,
если на нём работает UART связи с ПК. Отключение всех исключений не заменяет
очистку использованной периферии.

Штатный путь ядра: deinit прокси, если включён → port_deinit_all →
port_application_run. Приложение запускается из main, в привилегированном
режиме с MSP. Для показанных портов условие перехода — PRIMASK = 0;
IRQ использованной периферии при этом уже отключены.

После загрузки нового MSP функция перехода не обращается к локальным данным
на старом стеке. Используй короткую ассемблерную последовательность своего
компилятора, как в
[AT32F435 port_application_run.c](hal/at32f435vgt7/port/src/port_application_run.c).
Не копируй IAR __stackless/синтаксис ассемблера в GCC без адаптации.

VTOR настраивает ПРИЛОЖЕНИЕ до включения своих IRQ. Vendor SystemInit может
снова установить VTOR в начало Flash, поэтому проверь весь startup-путь
приложения, не только действие загрузчика. Для CPU без VTOR способ
переноса векторов должен быть определён отдельно.

## 8. Подключи исходники и настройки сборки

Для обычного загрузчика нужны:

- `core/src/`: bootloader.c, binex-lib.c, crc16.c, monocypher.c, utils.c;
- `hal/<mcu>/port/src/`: port_flash.c, port_application_run.c;
- один startup, один SystemInit и нужные реализации SDK;
- исходники платы: main, bootloader_port.c, поток, FIFO, hw_conf.

Include paths задавай относительно файла проекта:

```text
<project>/
<project>/config/
<project>/project/inc/
<project>/project/hw_conf/inc/
<PolyBoot>/core/inc/
<PolyBoot>/hal/<mcu>/CMSIS/inc/
<PolyBoot>/hal/<mcu>/SPL/inc/
<PolyBoot>/hal/<mcu>/port/inc/
<toolchain CMSIS Core include, если используется>
```

Проверь device define, CPU/FPU, ABI, endian, startup и отладочный Flash loader.
Выбери нужный vendor conf, а не случайный заголовок соседнего демо из-за
порядка include paths. Полная vendor-карта памяти не заменяет ограниченный
linker загрузчика.

Общие CMSIS-заголовки бери из toolchain или SDK. Не добавляй вторую
несовместимую версию CMSIS ради устранения ошибки include. При другом
компиляторе нужны его startup, scatter/linker script и переход. Проверяй map,
а не только успешность компиляции C.


Для IAR можно проверить выбранную конфигурацию командой:

```text
iarbuild <project>.ewp -make Debug -log warnings
```

Компилятор и пути к нему найди в рабочей среде. Режим оптимизации, FPU/ABI,
размеры стека и heap должны быть заданы явно. Конфигурация с именем Debug
сама по себе не требует BOOTLOADER_DBG_MODE или отключения проверки MAC.

## 9. Несколько экземпляров Binex

API: [binex-lib.h](core/inc/binex-lib.h). Каждый канал имеет статический
Binex_t, свой RX-буфер и функцию вывода. Глобальной binex_tx_callback больше
нет. Само ядро загрузчика остаётся одним экземпляром; слейвы обслуживает прокси.

| Функция | Поведение |
| --- | --- |
| `binex_init(&channel, callback)` | Сбросить экземпляр и закрепить функцию вывода; периферию не инициализирует |
| `binex_receiver_begin(&channel, buffer, capacity)` | Начать приём в буфер, сбросив незавершённый кадр |
| `binex_receiver(&channel, c)` | Обработать байт; c < 0 — данных нет. Возврат BINEX_PACK_NOT_RX, BINEX_PACK_RX или BINEX_PACK_BROKEN |
| `binex_get_rxpack_len(&channel)` | Длина payload; читать после BINEX_PACK_RX |
| `binex_transmitter_init(&channel, buffer, length)` | Начать передачу payload; буфер не копируется |
| `binex_transmit(&channel)` | Продолжать до BINEX_PACK_TX; если поток заполнен, возвращает BINEX_PACK_NOT_TX |

До обмена один раз вызывается Crc16Init; основной InitBootloader делает это
сам. Callback возвращает 1 для принятого байта и 0 для повтора позже.
TX-буфер неизменен до BINEX_PACK_TX. Это передача байтов в поток,
не обязательно физическое окончание UART: последнее проверяет
port_*_transfer_completed.

RX и TX одного экземпляра независимы при разных буферах. Не обслуживай
один экземпляр одновременно из ISR и main без отдельного решения
синхронизации. Обычно ISR обслуживает только FIFO. Состояния, CRC и счётчики
протокола не должны быть общими статическими переменными для всех UART.

Не меняй START F5, ESC F4, CRC и обрамление при портировании: это совместимость
с утилитой. Ядро уже формирует и разбирает кадры; аппаратный порт переносит
байты, не добавляя свой Binex поверх них.

## 10. Опциональный прокси для составного устройства

Для первого переноса оставь прокси выключенным. После проверки обычного
обновления добавь BOOTLOADER_USE_PROXY, core/src/bootloader_proxy.c и
реализацию [bootloader_proxy_port.h](core/inc/bootloader_proxy_port.h).
Пример файлов:
[at32f435vgt7-proxy-bootloader](project/at32f435vgt7-proxy-bootloader/README.md).
Полный формат команд — в [core/PROXY.md](core/PROXY.md).

| API | Контракт |
| --- | --- |
| `port_proxy_init_begin() / port_proxy_init_poll()` | Подготовить подсистему. Если нужен поиск слейвов, выполнить его здесь; для фиксированной платы поиск не обязателен. Повторный INIT освобождает прежний канал. |
| `port_proxy_get_slave_list(offset, ids, capacity, count)` | Выдать порцию стабильного списка. offset — индекс, не ID. Не писать больше capacity, задать count и вернуть PROXY_LIST_DONE/MORE/ERROR. При MORE count > 0. |
| `port_proxy_open_begin(slave_id) / port_proxy_open_poll()` | Освободить прежний канал, выдержать паузы, очистить FIFO, выбрать новый. DONE — полностью готов; ERROR оставляет слейвов отключёнными. |
| `port_proxy_close_begin() / port_proxy_close_poll()` | Закрыть канал, отменить текущую аппаратную операцию. Безопасно до INIT и при повторном CLOSE. Состояние ядра слейва не сбрасывать. |
| `port_proxy_deinit()` | Освободить все ресурсы перед приложением; допустим без предыдущего INIT |
| `port_proxy_serial_putc(c)` | c при приёме байта в поток или -1, без блокировки |
| `port_proxy_serial_getc()` | Следующий байт 0..255 или -1 |
| `port_proxy_serial_transfer_completed()` | 1 после опустошения FIFO и физического окончания передачи; иначе 0 |

Для init/open/close begin ничего не ожидает, poll делает короткий шаг
и возвращает PROXY_PORT_BUSY, PROXY_PORT_DONE или PROXY_PORT_ERROR.
Итог сохраняется до следующего begin. При быстрой операции первый poll
может сразу вернуть DONE. Общий модуль посылает A0 FF каждые 200 мс,
пока INIT не завершён. OPEN/CLOSE промежуточных ответов не имеют и должны
уложиться в таймаут ПК, обычно 500 мс. Порядок GPIO и таймеры принадлежат проекту.

Список содержит до 256 разных uint8_t ID. Значение 255 допустимо: нельзя
использовать его как sentinel закрытого канала. Смещение/счётчики списка —
uint16_t. count передаётся указателем; ids указывает на предоставленный
модулем буфер. Последняя порция может быть пустой, включая пустой список.
Модуль выдаёт порции последовательно и не хранит копию всего списка.
Список стабилен до следующего INIT.

В прокси-демо A0 подготавливает две шины, A1 всегда возвращает ID 0–11,
наличие устройств проверяет ПК. Это политика примера: число 12 не относится
к общему ядру. Проект с обнаружением формирует список при INIT.

В A4 передаётся payload. На физическом UART слейва обычный кадр Binex
всё равно необходим. Модуль сам использует второй Binex_t; порт поставляет
байтовый поток. Не разбирай команды слейва для пересылки: один запрос может
породить много сообщений прогресса. Каждый ответ передаётся с одним
префиксом A4, без статуса самого прокси. При потере ответа ПК получает
таймаут; выдумывать A4 01 нельзя.

Слейвы активированы до проксируемого обмена. Например, без таймаута их
jumper-функция возвращает 1 после проверки GPIO. Выбор CS только перекрывает
поток, ProcessBootloader продолжает вызываться. Открытие/закрытие UART
не вызывает повторный InitBootloader.

### Буферизация принадлежит проекту

Прокси пересылает все пакеты, не пропускает события и не управляет скоростью
слейва. Пока ответ передаётся ПК или мастер выполняет длинную команду,
FIFO слейва может не читаться. Рассчитай максимальный входной поток либо
реализуй согласованное регулирование в конкретном проекте.

Для payload P байт верхняя оценка кадра Binex с CRC:

```text
1 + 2 * (2 + P + 2) байт
START + максимально экранированные длина, payload и CRC
```

116 событий стирания по 10 байт и финальный ответ 2 байта дают оценку
`116 * 29 + 13 = 3377` байт. Это пример конкретной геометрии Flash,
не универсальное число. Учти другие ответы, время обслуживания FIFO,
скорости обоих направлений и разрядность индексов FIFO. Демо выделяет RX
по 16 Кбайт на каждый из двух UART; новый проект выбирает свой размер. Ошибки
и переполнение фиксируются, а не скрываются.

Большой FIFO не спасает от аппаратного overrun при запрещённых IRQ.
Проверяй длительность Flash-операций и порядок комплексного обновления:
запись мастера и интенсивный обмен со слейвами выполняются последовательно.

## 11. Настрой генератор обновлений

Сверь с используемой ревизией [PolyBootGen](https://github.com/DiMoonElec/PolyBootGen):

| Загрузчик | Секция генератора V2 |
| --- | --- |
| BOOTLOADER_APP_BEGIN | Memory/AppBegin |
| BOOTLOADER_APP_LENGTH | Memory/AppLength, включая хвост 32 байта |
| BOOTLOADER_DEVICE_ID_STRING | DeviceId |
| EncryptionKey, IntegrityKey | Keys/EncryptionKey, Keys/IntegrityKey |
| Обновляемое приложение | Binary: первый байт bin соответствует APP_BEGIN |
| Команды 79/7A | BootloaderVersion=2 и совместимая утилита ПК |
| Прокси у ROOT | ProxyVersion=1 |

В текущем V2 хэш — первые 16 байт SHA-256 исходного bin, до заполнения FF
и добавления хвоста. Генератор пишет хэш в Flash-образ и поле HASH контейнера,
затем вычисляет MAC образа и защищает блоки XChaCha20-Poly1305.
Ядро не вычисляет SHA-256: команда 79 после проверки MAC возвращает
сохранённые байты. Ответ — `79 00 [HASH:16]` (18 байт), при повреждении —
`79 01`. Информационная версия пакета, если есть, не входит в хвост
и не заменяет хэш.

Начало/длина области, ID и ключи совпадают для КАЖДОЙ секции. Одна секция
SLAVE используется всеми слейвами данного типа. Разным типам соответствуют
разные секции, а не отдельный файл на каждый числовой ID.

Raw bin приложения без сформированного хвоста не является готовым образом
для проверки целостности. Прежние пакеты с версией перед MAC несовместимы
с новым смыслом команды 79. Совпавший MAC не определяет формат хвоста:
ядро не отличит старую раскладку автоматически.

## 12. Порядок проверки и критерии готовности

1. Собери минимальное демо без прокси и общей шины. Проверь map: векторы,
   readonly-секции, RAM/стек, размер загрузчика и отсутствие пересечений.
   Не скрывай переполнение увеличением области без согласования нового
   адреса приложения.
2. На плате проверь частоты, реальную длительность SysTick и скорость UART.
   Добейся ACTIVATE и правильного GET_DEVICE_ID до операций Flash.
3. Собери приложение по APP_BEGIN с миганием по SysTick. Оно само настраивает
   VTOR и периферию: проверяется переход и работа IRQ, не только выполнение
   Reset_Handler.
4. Создай актуальный xbin. До/после обновления проверь границы приложения,
   загрузчик и настройки. Проверь первый/последний сектор, границу банков
   при наличии и фактическое FF после стирания.
5. Обнови приложение утилитой. Проверь запись, финальный MAC,
   GET_FIRMWARE_HASH и совпадение с HASH пакета. Проверь передачу F4/F5,
   то есть экранирование на реальных данных.
6. Проверь командный запуск и автозапуск после питания по выбранной политике.
   Учитывай время начального расчёта MAC при измерении ожидания.
7. Проверь отсутствие/повреждение образа и прерванное обновление: базовый
   загрузчик не запускает образ с неправильным MAC. После повреждения
   байта без изменения MAC команда 79 отвечает 79 01.
8. Проверь паузы Flash/MAC, watchdog, FIFO и возврат из критических секций.
   Таймаут ПК выбирается по реальному времени ответа.
9. Затем добавляй раннюю активацию и особенности платы. Для прокси проверь
   оба UART/все типы каналов, OPEN без CLOSE, повторный CLOSE, неверный ID,
   отсутствующего слейва и максимальную серию событий без потерь.
   CLOSE не сбрасывает состояние ядра слейва.

Порт готов, когда API реализован полностью, сборка укладывается
в согласованные границы, параметры совпадают с генератором, а проверки
на плате подтверждены. Без платы результат называется «порт собран,
аппаратно не проверен».

В итоговый отчёт включи:

- файлы HAL/проекта и версию/источник vendor-библиотек;
- частоты, интерфейс/пины, политику активации;
- карту загрузчик/приложение/хэш/MAC/настройки, компилятор и его настройки;
- размеры code/readonly data/readwrite data, стек и размеры FIFO;
- аппаратные проверки и оставшиеся ограничения;
- команды сборки/генерации или README проекта с этими действиями.
